最初に小さな機能をプロジェクトに追加しました。しかし、より大規模な変更には、堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できます。このレッスンから数回にわたり、Issue から新機能を作成し、コードが有効で、機能が期待どおりに動作することを確かめて、プロジェクトにマージするまでの、一般的なエージェント主導の開発プロセスを実践します。

> [!NOTE]
> 機能のワークフローでは、同じセッションを続けて使います。通常、ファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは主要な概念に集中するため手順を簡略化しています。

このレッスンでは、次の作業を行います。

- GitHub Issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を決めます。
- **Autopilot** モードで機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能 PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がゲームをカテゴリやパブリッシャーで絞り込めるようにする必要があります。バックログの Issue には機能が説明されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードで方針を決めてから、範囲を定めた実装を Autopilot に任せます。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本の重要性は増します。多くの開発者は、次のような流れで作業します。

1. 実装内容の詳細が記載された Issue を開きます。
2. 実装計画を作成します。
3. コードを作成してレビューします。
4. テストを実行し、コードを検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 詳細な手順はチームや Organization によって異なりますが、ほとんどは上記の流れに沿っています。

この標準的な進め方に従うと、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビューと検証を受けるようになります。

## セッションモード

**セッションモード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントが変更を提案し、次に進む前に利用者の入力を待ちます。
- **Plan**: エージェントが計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが完全に自律してコードを書き、テストを実行し、入力を待たずに反復します。

まず Plan モードで計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。既存の **Allow users to filter games by category and publisher** Issue を開きます。テンプレートに含まれているため、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード選択から **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで見つからない場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了してから再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## 絞り込み機能を計画する

計画を立てると、Copilot がコードを書く前にアプローチをレビューできます。Issue から始めたため、Copilot は機能のリクエストをすでにコンテキストとして持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、Issue の受け入れ条件に照らし合わせて計画を確認します。カテゴリとパブリッシャーの絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせ方や、該当するゲームがない場合の動作など、不明確な内容について話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。計画の範囲は、絞り込みの実装とテストに絞ります。PR は品質のワークフローを終えてから作成します。計画を承認する前に修正を依頼し、後の検証に使えるよう Issue の URL と合意した説明を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認しただけでモードが自動的に切り替わるとは限らないため、現在のモードを確認し、モード表示が **Autopilot** になっていることを確認します。

Copilot は実装に取りかかります。計画に沿ってコードを生成し、テストを実行しながら、作業を反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードは、他のコードと同じようにマージ前にレビューします。コードをレビューしてサイトを実行し、すべて問題なく動くことを確認しましょう。

1. **Changes** を開き、絞り込み機能の実装とテストを確認します。
2. 複数カテゴリやパブリッシャーの組み合わせも含め、結果を Issue と承認した追加要件に照らし合わせます。既存のリポジトリの指示に従っていることも確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、影響するチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカルサーバーを再利用することがあります。テスト対象が前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認しましょう。アプリを起動し、前と同じようにブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトで、アプリを起動してブラウザーキャンバスで開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選択し、結果が一致することを確認します。フィルターを解除してからパブリッシャーを選択し、結果を確認します。
4. カテゴリとパブリッシャーを組み合わせ、Issue と承認した計画に沿う結果になることを確認します。複数カテゴリに対応している場合は、合意した組み合わせ方も検証します。
5. 一致するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットして、全件が表示されることも確認します。
6. 確認が終わったら、次のプロンプトでこのセッションが起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けてセッションを保持する

絞り込み機能の PR は、まだ作成したりマージしたりしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム指示を絞り込み機能に適用し、スキルと QA を改善してから、レッスン 8 で PR を作成してマージします。開発サーバーを停止した後、セッションをそのままにしておき、次のレッスンで同じセッションに戻ります。
